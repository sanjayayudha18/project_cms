## Tujuan & Scope
CROWN menyimpan saldo akhir harian setiap rekening escrow vault vendor dari file harian Corebanking, sebagai satu-satunya sumber "saldo escrow" untuk kategorisasi vault (5.3) dan Cek Escrow (5.8).
- Masuk: migrasi `042` (`escrow_batch_files`, `escrow_batch_rows`), ETL Python `backend_python/escrow/`, file type `escrow` di `eod_retry_scheduler` (scan, retry, SLA, halaman EOD Monitoring yang sudah ada), muat ulang riwayat 6 bulan (bila Corebanking menyediakan, OPEN-6).
- Tidak termasuk: rata-rata 6 bulan / bulan berjalan + kategori H/M/L (5.3, memakai `ClassifyCashCountVault` dari 5.1); Selisih Cek Escrow (5.8); Monitoring Limit CIS (ditunda, A6 — hanya pemakai tabel ini nanti); rekonsiliasi escrow vs posisi kas CMS (CLAUDE.md §5 "Escrow reconciliation", Phase 4, parkir); layar baru selain EOD Monitoring.

## Acceptance Criteria
- **AC-5.2-01** (K3): file harian Corebanking yang diletakkan MFT di `FTP_DATA/ESCROW/` (nama/pola file OPEN-1) diproses oleh ETL Python; satu baris file = satu saldo akhir satu rekening pada satu tanggal saldo, disimpan di `escrow_batch_rows` beserta referensi ke `escrow_batch_files`.
- **AC-5.2-02** (CLAUDE.md §5 Idempotency): file dengan SHA-256 yang sama tidak diproses dua kali (tercatat di `import_jobs`, `source = 'escrow'`); file baru untuk tanggal saldo yang sama (hash beda) menjadi versi baru: versi lama ditandai `superseded` dan baris lamanya tidak lagi dibaca, dalam satu tx.
- **AC-5.2-03** (CLAUDE.md §6): saldo di-parse sebagai `Decimal` dan disimpan `numeric(20,2)` dengan mata uang eksplisit (`IDR`); format angka/tanggal mengikuti contoh file (OPEN-2). Nilai yang tidak bisa di-parse → seluruh file gagal (all-or-nothing), tidak ada baris parsial.
- **AC-5.2-04** (L707–L708, migrasi 040): nomor rekening disimpan apa adanya (12 digit, pola `vendor_vaults.escrow_cash/escrow_atm`); baris tidak di-FK ke vault — pemetaan rekening → vault/area dilakukan saat baca, sehingga satu escrow yang dipakai beberapa vendor tetap satu baris saldo.
- **AC-5.2-05** (L601, L749–L753): pembaca (5.3, 5.8) bisa mendapat saldo harian per rekening per tanggal hanya dari file versi aktif yang statusnya `completed`; file `processing`/`failed` tidak pernah terbaca (CLAUDE.md §14 handoff).
- **AC-5.2-06** (data-map "Daily escrow balance"): setelah file selesai, `escrow_batch_files` mencatat jumlah baris, jumlah rekening yang tidak cocok dengan `vendor_vaults` aktif (`escrow_cash`/`escrow_atm`), dan jumlah rekening vault aktif yang tidak ada di file — sebagai peringatan di EOD Monitoring, tidak menggagalkan file.
- **AC-5.2-07** (CLAUDE.md §14 Scheduler): file type `escrow` ikut scan/retry `eod_retry_scheduler` (05:00–09:00 WIB, auto-retry maks 3), dengan SLA per OPEN-3; lewat SLA → `late_detections`; status per file terlihat di halaman EOD Monitoring (ADMIN/APPACCESS) tanpa layar baru.
- **AC-5.2-08** (CLAUDE.md §5 Audit, keputusan S4): aksi sistem (scan, proses, retry, supersede) tercatat di `retry_audit_logs`; retry manual dari halaman EOD Monitoring oleh user tercatat di `audit_logs` dalam tx yang sama (pola `import_jobs` yang ada).
- **AC-5.2-09** (L601, OPEN-6): riwayat saldo minimal 6 bulan sebelum kategorisasi pertama dapat dimuat lewat jalur ETL yang sama (satu file per tanggal atau satu file multi-tanggal — OPEN-6), idempotent, di luar jam 07:00–20:00 (CLAUDE.md §14).

## Design
### Data
Migrasi **`042_escrow_balances.sql`** (nomor bebas per 2026-11-16 — terakhir `041`), satu tx, forward-only, rollback di header. Nama tabel sudah disetujui (CLAUDE.md §3 Integration); **kolom menunggu contoh file** — draft:

1. **`escrow_batch_files`**: `id bigint identity · import_job_id bigint FK import_jobs NOT NULL UNIQUE · file_name text NOT NULL CHECK (1–255) · balance_date date NOT NULL` *(bila satu file = satu tanggal; OPEN-4)* `· status text CHECK (processing|completed|failed|superseded) · row_count int · unmatched_account_count int · missing_account_count int · superseded_at timestamptz NULL · created_at · completed_at`. Unique parsial `(balance_date) WHERE status = 'completed' AND superseded_at IS NULL` (satu versi aktif per tanggal).
2. **`escrow_batch_rows`**: `id bigint identity · file_id bigint FK escrow_batch_files NOT NULL · account_number text NOT NULL CHECK (^[0-9]{12}$)` *(OPEN-2: panjang di file)* `· balance_date date NOT NULL · closing_balance numeric(20,2) NOT NULL` *(boleh negatif? OPEN-5)* `· currency_code char(3) NOT NULL DEFAULT 'IDR' · raw jsonb NULL` (kolom file lain yang tidak dipetakan, untuk penelusuran) `· created_at`. Unique `(file_id, account_number, balance_date)`. Index `(account_number, balance_date)` untuk pembaca 5.3/5.8.
3. View **`escrow_daily_balances`** (opsional, diputuskan gerbang 1): baris dari file `completed` + tidak `superseded` saja — satu tempat untuk aturan AC-05 supaya 5.3/5.8/CIS tidak mengulangnya.

Baris mentah dipisah dari ringkasan (CLAUDE.md §6); ringkasan/rata-rata tidak disimpan di fase ini. Tabel append-only (supersede = tandai file, bukan hapus baris); masuk `no_hard_delete_test.go`. Retensi: simpan selamanya sampai diputuskan lain (OPEN-7).

## Pertanyaan Terbuka & Risiko
Pertanyaan untuk PO / tim Corebanking (syarat gerbang 1, lanjutan K3):
- **OPEN-1** Nama/pola file, format (CSV/TXT fixed-width/XLSX), encoding, header ada atau tidak, delimiter.
- **OPEN-2** Kolom: nomor rekening (panjang, ada nol depan?), tanggal saldo (format), saldo akhir (pemisah ribuan/desimal), mata uang, kolom lain (nama rekening, CIF, saldo awal, mutasi?).
- **OPEN-3** Jadwal kirim via MFT (jam berapa file H-1 tersedia) → SLA di scheduler. Perlu tersedia sebelum 07:00 bila 5.8 Cek Escrow memakai saldo H-1 pada hari cash count.
- **OPEN-4** Isi file: hanya rekening escrow vault vendor, atau semua rekening (perlu filter)? Satu file = satu tanggal?
- **OPEN-5** Saldo negatif mungkin? Arti nilai kosong / `-` (L737): 0 atau tidak ada data? Rekening tanpa baris pada suatu hari: dianggap 0 atau dilewati saat rata-rata (keputusan di 5.3, tapi bentuk data di sini).
- **OPEN-6** Riwayat 6 bulan untuk kategorisasi pertama (L601): bisa dikirim Corebanking sekali (backfill)? Bila tidak, kategori awal tertunda 6 bulan atau perlu cadangan (K3 opsi C — saldo DSR vault).
- **OPEN-7** Retensi baris saldo (minimal 6 bulan + bulan berjalan untuk 5.3; laporan 5.9 mungkin lebih lama).

Risiko:
- Format file baru diketahui saat contoh datang; AC-01…AC-03 dan Data bisa berubah → gerbang 1 dihitung dari versi setelah revisi (nomor AC lama tidak dipakai ulang).
- Data-map lama menyebut sumber "link ke SIBS"; K3 memilih Corebanking. Bila file ternyata dari SIBS, jalur sama, hanya nama/format — tidak mengubah pembagian fase.
- Rekening escrow di `vendor_vaults` diisi lewat master data (migrasi 040); rekening kosong → peringatan AC-06 "tidak ada di file" tidak muncul untuk vault itu, dan 5.3 tidak bisa mengkategorikan vault tersebut.
