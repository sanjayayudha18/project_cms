## Kondisi awal (dari `backend/migrations/001_baseline_schema.sql`)
- `vendors` — CRUD ✅ (`/api/v1/admin/vendors`), langsung apply + audit. Belum ada `legal_name`, `npwp`.
- `vendor_branches` — tanpa CRUD, tanpa `deleted_at`.
- `vendor_vaults` (FK `vendor_branch_id`) — tanpa CRUD; belum ada alamat/koordinat/jam operasional/kategori/`deleted_at`. Kolom `type` isinya belum dicek.
- `vendor_pics` — **belum ada**.
- `vendor_packages`, `atm_vendor_packages` — tanpa CRUD; hanya UNIQUE `(atm_id, vendor_package_id, effective_start_date)`, belum ada cegah-tumpang-tindih periode.
- `atms` — CRUD ✅ (`/api/v1/admin/atms`), langsung apply + audit.
- Approval engine: `internal/approval/orchestrator.go` — level dari `approval_policies (document_type, amount)`; `approval_requests` tanpa payload; belum ada callback on-approved.

- [x] **T5.4** Import confirm: semua baris valid → change request batch (`batch_id` sama), satu approval untuk satu batch. Idempotent per file hash (file sama → kembalikan batch yang sudah ada).
  - Catatan implementasi: `POST /api/v1/admin/master-data/import/{entity}/confirm` (upload sama dengan dry-run). Migrasi `005_master_data_import_batches.sql`: tabel `master_data_import_batches(entity, file_hash sha256, maker_id, row_count)` + FK `master_data_change_requests.batch_id`. Respons **202** `{batch_id, rows, approval_request_id, existing:false, entity}`; file yang sama → **200** dengan batch lama (`existing:true`). File berisi error → **422** `{errors:[{row,field,message}]}` (tak ada yang di-stage); tak ada perubahan → 422; baris bentrok dengan change pending entitas lain → 409 ("baris N").
  - **Cara staging:** `MasterDataImporter.Confirm` menjalankan setiap baris melalui service admin per-entitas yang SAMA dengan endpoint tunggal, tetapi dengan *collector* sebagai `Submit` — validasi, payload, dan snapshot `before` identik tanpa duplikasi kode. Hasil kolektor ditulis sebagai satu batch (`repository.MasterDataImportBatchRepository.Create`: satu transaksi, advisory lock per (entity, hash), semua baris atau tidak sama sekali). Satu `approval_requests` dibuat untuk batch (`document_id` = change request pertama/"head") dan ditautkan ke semua baris.
  - **Idempotensi:** kunci = (entity, SHA-256 isi file). Dicek SEBELUM validasi (setelah batch diapply, file yang sama tak lagi lolos validasi "sudah ada", tapi harus tetap menjawab "sudah"). Batch yang ditolak (rejected) atau stale boleh diunggah ulang → batch baru. Jika proses mati antara staging dan submit approval, upload ulang file yang sama menyelesaikan submit approval-nya (pemulihan).
  - **Apply/reject batch** (`masterdata_approval.go`): approve pada approval batch meng-apply SEMUA baris dalam SATU transaksi (`applyOne` per baris; gagal satu = rollback semua; baris yang gagal mencatat error-nya, head mencatat "batch rolled back"); reject menolak seluruh baris batch.
  - Aturan baris (ditambahkan ke dry-run): perubahan data + perubahan `is_active` dalam satu baris ditolak (butuh dua change request untuk entitas yang sama → bentrok dengan indeks unik pending); mengubah data baris nonaktif ditolak ("aktifkan dulu"). Update murni = op update; hanya `is_active` berubah = enable/disable (`ImportRow.Toggle`).
  - Tes: unit `masterdata_import_test.go` (+toggle), handler (202/200/422/409/403/401), integrasi `masterdata_import_confirm_integration_test.go`: satu batch = satu approval, idempoten per file (termasuk setelah apply), apply atomik, satu baris gagal ⇒ seluruh batch rollback, reject menolak semua + file boleh diunggah ulang, file invalid tak men-stage apa pun, export tanpa perubahan = `ErrImportNothingToDo`, identitas maker. Tabel uji bersih (vendors 6, batches/changes/approvals 0).
  - Batas yang diketahui: tampilan inbox approval untuk batch (daftar baris/diff) belum ada — Fase 6 (T6.4); integrasi apply-batch diuji lewat vendors (semua applier memakai jalur `applyOne` yang sama).
  - **Model:** Opus, **Effort:** High — batch change request + idempotency per file hash lewat maker-checker; salah kunci hash merusak keamanan re-run.

  - **⚠️ Found and fixed a real integration-test-harness bug while writing the staleness test** (not a production bug): `masterdata_approval_integration_test.go` originally reused the `rolemgmt`-style "outer tx doubles as both repo's DBTX and the apply Pool" convention. That works for `rolemgmt.PermissionService` (everything in one transaction), but `MasterDataApprovalService` deliberately spans **two** transactional scopes — `repo` (durable, must survive an apply-tx rollback) and `pool.Begin()` (the rollback-able apply tx). Because `pgx.Tx.Begin()` implements nested transactions as **savepoints on the same physical session**, a `MarkStale` write issued through the "outer tx" repo *after* the nested apply tx had begun was silently undone by that nested tx's `ROLLBACK TO SAVEPOINT` on cleanup — even though it went through a different Go `pgx.Tx` value. **Fixed** by rewriting the harness to use the real `*pgxpool.Pool` directly for both `repo` and `pool` (matching production topology exactly, where they're genuinely different connections) and doing explicit ID-tracked cleanup (`testHelpers.cleanup()`) instead of relying on an outer rollback. Verified no leftover rows after a full run. **Lesson for future services with this same split-durability shape** (repo writes that must survive a rolled-back sub-transaction): don't reuse the single-outer-tx-as-pool harness convention; use a real pool + explicit cleanup instead.
