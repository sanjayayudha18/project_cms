## Task 1 — Migration: ATM search index — DONE (2026-09-16)

- [x] Created `backend/migrations/039_admin_atm_search_index.sql` (additive, `BEGIN;…COMMIT;`, WHY/SAFETY/rollback header, `IF NOT EXISTS` throughout) — `CREATE EXTENSION IF NOT EXISTS pg_trgm` + GIN `atms_terminal_id_trgm_idx ON public.atms USING gin (terminal_id gin_trgm_ops)`. Built inline, not `CONCURRENTLY`: `atms` is a small master table, so an atomic migration is worth more than dodging a negligible lock window.
- [x] **Test — PASSED** against the local `cms` DB (PG 18.3, `atms` = 1904 real rows). Note `DATABASE_URL` in `backend/.env` points at `host.docker.internal` (a from-inside-container alias); from the host it must be reached via `localhost`.
  - Applies clean: `BEGIN / CREATE EXTENSION / CREATE INDEX / COMMIT`.
  - Idempotent: second run is a clean no-op (`IF NOT EXISTS` NOTICEs only, still commits).
  - `\d atms` shows `atms_terminal_id_trgm_idx gin (terminal_id gin_trgm_ops)` alongside the pre-existing `atms_terminal_id_uq` btree.
  - `EXPLAIN (ANALYZE, BUFFERS)` on `terminal_id ILIKE '%123%'` plans **`Bitmap Index Scan on atms_terminal_id_trgm_idx`** — 0.305 ms, vs 0.642 ms for the same query with `enable_bitmapscan=off` (forced seq scan).
- [x] **Known limit recorded (not a defect):** pg_trgm only indexes patterns of **≥ 3 characters**. A 1–2 char `q` still plans a seq scan (verified). Acceptable — the short-query scan is cheap — but Task 7's search box should not be assumed index-backed on every keystroke. Documented in the migration header.
- **Demo:** ✅ query plan on the live 1904-row `atms` avoids the seq scan for ≥3-char search terms (evidence above).
