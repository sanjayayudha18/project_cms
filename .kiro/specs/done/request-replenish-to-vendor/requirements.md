# Requirements Document

## Introduction

Vendor Request feature for the CMS (Cash Management System) at CIMB Niaga. This feature enables internal operations staff (Cash Management team) to create cash replenishment orders to CIT (Cash-in-Transit) vendors based on DMAA ATM forecasting data. The workflow follows a state machine pattern with maker-checker approval aligned to the D-3 hierarchy. DMAA forecast data is already available in PostgreSQL via an existing ETL pipeline (dmaa_files + dmaa_atm_forecast tables). The feature covers: browsing forecast data, selecting ATM orders, composing a vendor request, submitting for approval, and transitioning approved requests into actionable orders.

## Glossary

- **Vendor_Request**: A cash replenishment order composed of one or more forecast line items, created by a Maker and submitted for approval to a Checker before becoming actionable for the CIT vendor
- **Vendor_Request_Item**: A single line item within a Vendor_Request, referencing a specific ATM forecast row (atm_id, periode_pred, denom, amount_replenish)
- **DMAA_Forecast**: The ATM cash demand forecast data imported from the DMAA system, stored in the dmaa_atm_forecast table with columns: atm_id, dmaa_file_id, periode_pred, denom, amount_replenish, amount_refund
- **Forecast_Browser**: The frontend page that displays DMAA forecast data filtered by date, allowing the user to select items for inclusion in a Vendor_Request
- **Maker**: An internal user (role ATM-USER or BRANCH-ATM-USER) who creates and submits a Vendor_Request for approval
- **Checker**: An internal user (role ATM-SPV or BRANCH-ATM-SPV) who reviews and approves or rejects a submitted Vendor_Request, following the D-3 hierarchy
- **CIT_Vendor**: The external Cash-in-Transit vendor company that executes the physical cash replenishment at ATM locations
- **Request_State_Machine**: The state machine governing the lifecycle of a Vendor_Request with states: draft, pending_approval, approved, rejected, processing, completed, cancelled
- **Forecast_Date**: The target replenishment date (periode_pred) used to filter DMAA forecast data for creating a Vendor_Request
- **Vendor_Request_Service**: Backend service layer orchestrating the creation, state transitions, and approval flow of Vendor Requests
- **Vendor_Request_Handler**: HTTP handler layer exposing REST API endpoints for Vendor_Request operations
- **Audit_Log**: A record capturing who performed what action on a Vendor_Request and when, stored in the database for compliance and traceability
- **Denomination**: The banknote value (50000 or 100000 IDR) for a cash replenishment line item
- **Amount_Replenish**: The total IDR amount to be replenished for a specific ATM, denomination, and date

## Requirements

### Requirement 1: Vendor Request Database Schema

**User Story:** As a developer, I want a database schema for vendor requests, so that the system can persist request data with proper state tracking, audit trail, and referential integrity to DMAA forecast data.

#### Acceptance Criteria

1. THE Migration_Service SHALL create a `vendor_requests` table with columns: id (BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY), request_number (TEXT UNIQUE NOT NULL), forecast_date (DATE NOT NULL), status (TEXT NOT NULL DEFAULT 'draft'), notes (TEXT), created_by (BIGINT NOT NULL FK to users ON DELETE RESTRICT), approved_by (BIGINT FK to users ON DELETE RESTRICT), rejected_by (BIGINT FK to users ON DELETE RESTRICT), rejection_reason (TEXT), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), updated_at (TIMESTAMPTZ NOT NULL DEFAULT NOW()), submitted_at (TIMESTAMPTZ), approved_at (TIMESTAMPTZ), rejected_at (TIMESTAMPTZ)
2. THE Migration_Service SHALL create a `vendor_request_items` table with columns: id (BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY), vendor_request_id (BIGINT NOT NULL FK to vendor_requests ON DELETE CASCADE), atm_id (TEXT NOT NULL), periode_pred (DATE NOT NULL), denom (INT NOT NULL CHECK denom > 0), amount_replenish (BIGINT NOT NULL CHECK amount_replenish >= 0), amount_refund (BIGINT NOT NULL DEFAULT 0 CHECK amount_refund >= 0), created_at (TIMESTAMPTZ NOT NULL DEFAULT NOW())
3. THE Migration_Service SHALL add a CHECK constraint on vendor_requests.status restricting values to: 'draft', 'pending_approval', 'approved', 'rejected', 'processing', 'completed', 'cancelled'
4. THE Migration_Service SHALL add a UNIQUE constraint on vendor_request_items (vendor_request_id, atm_id, periode_pred, denom) to prevent duplicate line items within the same request
5. THE Migration_Service SHALL create indexes on vendor_requests (status), vendor_requests (forecast_date), vendor_requests (created_by), and vendor_request_items (atm_id, periode_pred) for query performance
6. THE Migration_Service SHALL create a BEFORE UPDATE trigger on vendor_requests that executes the existing `set_updated_at()` function to automatically maintain the updated_at timestamp, consistent with other tables in the schema
7. THE Migration_Service SHALL wrap the entire up migration in a transaction (BEGIN/COMMIT) and include a reversible down migration that drops the trigger, vendor_request_items table, and vendor_requests table in dependency order (trigger first, then child table, then parent table)

### Requirement 2: Vendor Request State Machine

**User Story:** As an operations manager, I want vendor requests to follow a controlled lifecycle, so that requests cannot skip approval steps and every state change is auditable.

#### Acceptance Criteria

1. THE Request_State_Machine SHALL define the following valid state transitions: draft→pending_approval (submit), draft→cancelled (cancel), pending_approval→approved (approve), pending_approval→rejected (reject), pending_approval→cancelled (cancel), rejected→draft (revise), approved→processing (process), processing→completed (complete), processing→failed (fail)
2. IF a state transition is attempted that does not exist in the valid transitions list, THEN THE Vendor_Request_Service SHALL reject the request and return an error indicating the attempted transition is not allowed from the current state, without modifying the request's current state
3. WHEN a state transition occurs, THE Vendor_Request_Service SHALL write an Audit_Log entry containing: vendor_request_id, previous_state, new_state, action_performed, performed_by (user id), performed_at (timestamp), and optional metadata (rejection_reason for reject action)
4. THE Request_State_Machine SHALL enforce that only the Maker who created the request can perform submit, cancel (from draft), and revise actions
5. THE Request_State_Machine SHALL enforce that only a Checker (ATM-SPV or BRANCH-ATM-SPV) can perform approve and reject actions
6. IF a user who is not authorized for the attempted action performs that action, THEN THE Vendor_Request_Service SHALL reject the request and return an error indicating insufficient permissions, without modifying the request's current state
7. THE Request_State_Machine SHALL enforce that the Checker who approves or rejects a request is a different user from the Maker who created the request (four-eyes principle)
8. IF a Checker attempts to approve or reject a request they themselves created, THEN THE Vendor_Request_Service SHALL reject the request and return an error indicating the four-eyes principle violation, without modifying the request's current state
9. WHEN a request transitions to pending_approval, THE Vendor_Request_Service SHALL record submitted_at timestamp
10. WHEN a request transitions to approved, THE Vendor_Request_Service SHALL record approved_at timestamp and approved_by user id
11. WHEN a request transitions to rejected, THE Vendor_Request_Service SHALL record rejected_at timestamp, rejected_by user id, and rejection_reason (mandatory non-empty text, maximum 1000 characters)
12. THE Request_State_Machine SHALL enforce that only a Checker (ATM-SPV or BRANCH-ATM-SPV) can perform the cancel action from pending_approval state

### Requirement 3: Browse DMAA Forecast Data

**User Story:** As a Cash Management staff member, I want to browse DMAA forecast data filtered by date, so that I can see which ATMs need cash replenishment and select items for a vendor request.

#### Acceptance Criteria

1. THE Vendor_Request_Handler SHALL expose GET /api/v1/vendor-requests/forecast endpoint accepting a required query parameter `forecast_date` (DATE format YYYY-MM-DD)
2. WHEN the forecast_date parameter is provided, THE Vendor_Request_Service SHALL return rows from dmaa_atm_forecast where periode_pred matches the forecast_date, ordered by atm_id ascending, paginated according to page and page_size parameters
3. THE endpoint SHALL support query parameters: page (default 1, minimum 1), page_size (default 20, maximum 100), and optional `atm_id` for filtering results by a specific ATM identifier (partial match, case-insensitive, minimum 1 character)
4. THE response payload SHALL include for each row: atm_id, periode_pred, denom, amount_replenish, amount_refund, and the dmaa_file_id for traceability
5. THE response SHALL include pagination metadata: total_count, page, page_size, total_pages
6. IF no DMAA forecast data exists for the provided forecast_date (or after applying atm_id filter), THEN THE Vendor_Request_Handler SHALL return an empty array with HTTP 200 and total_count of 0
7. IF the forecast_date parameter is missing or not a valid date in YYYY-MM-DD format, THEN THE Vendor_Request_Handler SHALL return HTTP 400 with a structured validation error identifying the invalid parameter
8. IF the page or page_size parameters are provided but are not positive integers or page_size exceeds 100, THEN THE Vendor_Request_Handler SHALL return HTTP 400 with a structured validation error identifying the invalid parameter
9. THE endpoint SHALL require authentication and authorize roles: ADMIN, ATM-USER, ATM-SPV, BRANCH-ATM-USER, BRANCH-ATM-SPV

### Requirement 4: Create Vendor Request (Draft)

**User Story:** As a Maker, I want to create a new vendor request by selecting forecast items, so that I can compose an order for the CIT vendor.

#### Acceptance Criteria

1. THE Vendor_Request_Handler SHALL expose POST /api/v1/vendor-requests endpoint accepting a JSON body with: forecast_date (DATE, required), items (array of {atm_id, periode_pred, denom, amount_replenish}, minimum 1 item required), and notes (TEXT, optional, max 500 characters)
2. WHEN a valid request is received, THE Vendor_Request_Service SHALL create a new Vendor_Request in draft status with an auto-generated request_number following the pattern VR-YYYYMMDD-NNNN (where YYYYMMDD is the forecast_date and NNNN is a zero-padded sequential number per date)
3. THE Vendor_Request_Service SHALL create Vendor_Request_Item records for each item in the request, copying atm_id, periode_pred, denom, and amount_replenish from the request payload
4. IF any item in the request references an atm_id + periode_pred + denom combination that does not exist in dmaa_atm_forecast, THEN THE Vendor_Request_Service SHALL return HTTP 400 with an error identifying the invalid items
5. IF any item in the request has an amount_replenish value that differs from the corresponding dmaa_atm_forecast row, THEN THE Vendor_Request_Service SHALL use the amount_replenish value from the request payload (allowing manual override) but log the discrepancy in the Audit_Log
6. THE Vendor_Request_Service SHALL validate that no duplicate (atm_id, periode_pred, denom) combinations exist within the same request payload and return HTTP 400 if duplicates are found
7. WHEN creation succeeds, THE Vendor_Request_Handler SHALL return HTTP 201 with the created Vendor_Request including its id, request_number, status, forecast_date, items array, and timestamps
8. THE endpoint SHALL require authentication and authorize roles: ADMIN, ATM-USER, BRANCH-ATM-USER

### Requirement 5: Submit Vendor Request for Approval

**User Story:** As a Maker, I want to submit my draft vendor request for approval, so that a Checker can review and authorize the cash replenishment order.

#### Acceptance Criteria

1. THE Vendor_Request_Handler SHALL expose POST /api/v1/vendor-requests/{id}/submit endpoint
2. WHEN a valid submit request is received, THE Vendor_Request_Service SHALL transition the request from draft to pending_approval state
3. IF the request is not in draft state, THEN THE Vendor_Request_Service SHALL return HTTP 409 Conflict with an error indicating the current state does not allow submission
4. IF the request contains zero Vendor_Request_Items, THEN THE Vendor_Request_Service SHALL return HTTP 409 Conflict with an error indicating the request must contain at least one item before submission
5. IF the authenticated user is not the creator of the request (created_by does not match), THEN THE Vendor_Request_Service SHALL return HTTP 403 Forbidden with an error indicating only the request creator can submit
6. IF the vendor request with the given id does not exist, THEN THE Vendor_Request_Handler SHALL return HTTP 404 Not Found
7. WHEN submission succeeds, THE Vendor_Request_Handler SHALL return HTTP 200 with the updated Vendor_Request showing status=pending_approval and submitted_at timestamp
8. THE endpoint SHALL require authentication and authorize roles: ADMIN, ATM-USER, BRANCH-ATM-USER

---

### Requirement 6: Approve or Reject Vendor Request

**User Story:** As a Checker, I want to approve or reject pending vendor requests, so that only verified cash replenishment orders proceed to the CIT vendor.

#### Acceptance Criteria

1. THE Vendor_Request_Handler SHALL expose POST /api/v1/vendor-requests/{id}/approve endpoint
2. THE Vendor_Request_Handler SHALL expose POST /api/v1/vendor-requests/{id}/reject endpoint accepting a JSON body with rejection_reason (TEXT, required, min 1 non-whitespace character after trimming, max 500 characters)
3. WHEN a valid approve request is received, THE Vendor_Request_Service SHALL transition the request from pending_approval to approved state
4. WHEN a valid reject request is received, THE Vendor_Request_Service SHALL transition the request from pending_approval to rejected state and record the rejection_reason
5. IF the request is not in pending_approval state, THEN THE Vendor_Request_Service SHALL return HTTP 409 Conflict with an error indicating the current state does not allow this action
6. IF the authenticated user is the same user who created the request (created_by), THEN THE Vendor_Request_Service SHALL return HTTP 403 Forbidden indicating self-approval or self-rejection is not allowed (four-eyes principle)
7. WHEN approval succeeds, THE Vendor_Request_Handler SHALL return HTTP 200 with the updated Vendor_Request showing status=approved, approved_at, and approved_by
8. WHEN rejection succeeds, THE Vendor_Request_Handler SHALL return HTTP 200 with the updated Vendor_Request showing status=rejected, rejected_at, rejected_by, and rejection_reason
9. THE approve and reject endpoints SHALL require authentication and authorize roles: ADMIN, ATM-SPV, BRANCH-ATM-SPV
10. IF the vendor request ID does not exist, THEN THE Vendor_Request_Handler SHALL return HTTP 404 with an error indicating the resource was not found
11. WHEN a vendor request transitions to approved or rejected state, THE Vendor_Request_Service SHALL write an entry to the audit log recording the action performed, the acting user, and a timestamp
12. IF the rejection_reason field is missing or contains only whitespace, THEN THE Vendor_Request_Handler SHALL return HTTP 422 with an error indicating that a non-empty rejection reason is required

4. IF the authenticated user is not the creator of the request (created_by does not match), THEN THE Vendor_Request_Service SHALL return HTTP 403 Forbidden with an error indicating only the request creator can revise
5. IF the vendor request with the given id does not exist, THEN THE Vendor_Request_Handler SHALL return HTTP 404 Not Found
6. WHEN revision succeeds, THE Vendor_Request_Handler SHALL return HTTP 200 with the updated Vendor_Request showing status=draft
7. THE endpoint SHALL require authentication and authorize roles: ADMIN, ATM-USER, BRANCH-ATM-USER

### Requirement 8: Update Vendor Request Items (Draft)

**User Story:** As a Maker, I want to add or remove items from my draft vendor request, so that I can adjust the order before submission.

#### Acceptance Criteria

1. THE Vendor_Request_Handler SHALL expose PUT /api/v1/vendor-requests/{id}/items endpoint accepting a JSON body with items (array of {atm_id, periode_pred, denom, amount_replenish}, minimum 1 item, maximum 1000 items)
2. WHEN a valid update request is received, THE Vendor_Request_Service SHALL replace all existing Vendor_Request_Items with the new items provided (full replacement strategy) within a single database transaction
3. IF the vendor request with the given id does not exist, THEN THE Vendor_Request_Handler SHALL return HTTP 404 Not Found
4. IF the request is not in draft state, THEN THE Vendor_Request_Service SHALL return HTTP 409 Conflict with an error indicating items can only be modified in draft state
5. IF the authenticated user is not the creator of the request (created_by does not match), THEN THE Vendor_Request_Service SHALL return HTTP 403 Forbidden with an error indicating only the request creator can modify items
6. THE Vendor_Request_Service SHALL apply the same validation rules as creation: no duplicate (atm_id, periode_pred, denom) combinations within the payload and each item must reference a valid row in dmaa_atm_forecast; IF validation fails, THEN THE Vendor_Request_Service SHALL return HTTP 400 with a structured error identifying the invalid or duplicate items
7. WHEN update succeeds, THE Vendor_Request_Handler SHALL return HTTP 200 with the updated Vendor_Request including its id, request_number, status, forecast_date, notes, the new items array, and timestamps
8. THE endpoint SHALL require authentication and authorize roles: ADMIN, ATM-USER, BRANCH-ATM-USER

### Requirement 9: List and View Vendor Requests

**User Story:** As a Cash Management staff member, I want to list and view vendor requests with filtering, so that I can track request status and find specific requests.

#### Acceptance Criteria

1. THE Vendor_Request_Handler SHALL expose GET /api/v1/vendor-requests endpoint returning a paginated list of Vendor Requests sorted by created_at descending (most recent first) as the default order

THE endpoint SHALL support query parameters: status (filter by one or more statuses from the valid set: draft, pending_approval, approved, rejected, processing, completed, cancelled, comma-separated), forecast_date (filter by forecast date, format YYYY-MM-DD), created_by (filter by creator user id), page (integer, minimum 1, default 1), page_size (integer, minimum 1, default 20, max 100)

THE response payload SHALL include for each request: id, request_number, forecast_date, status, notes, item_count (number of items), total_amount (sum of all item amount_replenish), created_by (with user full_name), approved_by (with user full_name if applicable), created_at, submitted_at, approved_at, rejected_at
5. THE response SHALL include pagination metadata: total_count, page, page_size, total_pages
6. THE Vendor_Request_Handler SHALL expose GET /api/v1/vendor-requests/{id} endpoint returning a single Vendor_Request with: id, request_number, forecast_date, status, notes, created_by (with user full_name), approved_by (with user full_name if applicable), rejected_by (with user full_name if applicable), rejection_reason, created_at, updated_at, submitted_at, approved_at, rejected_at, and an items array where each item includes: id, atm_id, periode_pred, denom, amount_replenish, amount_refund
7. IF the requested Vendor_Request does not exist or the id is not a valid identifier, THEN THE Vendor_Request_Handler SHALL return HTTP 404 Not Found
8. THE list and detail endpoints SHALL require authentication and authorize roles: ADMIN, ATM-USER, ATM-SPV, BRANCH-ATM-USER, BRANCH-ATM-SPV

### Requirement 11: Frontend Forecast Browser Page

**User Story:** As a Cash Management staff member, I want a page to browse DMAA forecast data by date and select items, so that I can efficiently compose vendor requests.

#### Acceptance Criteria

1. THE Forecast_Browser SHALL display a date picker input defaulting to the next business day (Monday–Friday, excluding Indonesian public holidays), allowing the user to select a Forecast_Date
2. WHEN a Forecast_Date is selected, THE Forecast_Browser SHALL fetch and display forecast data in a table with columns: checkbox (for selection), ATM ID, Denomination (formatted as IDR currency), Amount Replenish (formatted as IDR currency, right-aligned, tabular-nums), and Amount Refund (formatted as IDR currency, right-aligned, tabular-nums)
3. THE Forecast_Browser table SHALL use TanStack Table with sorting enabled on ATM ID, Denomination, and Amount Replenish columns, with a default sort of ATM ID ascending
4. THE Forecast_Browser SHALL provide a "Select All" checkbox in the table header that toggles selection of all visible (post-filter) rows
5. THE Forecast_Browser SHALL display a summary bar showing: number of selected items, total amount of selected items (formatted as IDR), and a "Create Vendor Request" primary action button (--red-500) that is enabled only when at least one item is selected
6. WHEN the user clicks "Create Vendor Request", THE Forecast_Browser SHALL navigate to the vendor request creation page passing the selected forecast items and the Forecast_Date via client-side route state
7. THE Forecast_Browser SHALL provide a text input for filtering by ATM ID (debounced, 300ms, partial match, case-insensitive) that filters the displayed table rows while preserving existing row selections
8. IF the forecast data is loading, THEN THE Forecast_Browser SHALL display a skeleton loading state following the design system patterns
9. IF no forecast data exists for the selected date, THEN THE Forecast_Browser SHALL display an empty state message indicating no data is available for the selected date
10. THE Forecast_Browser page SHALL be accessible from the sidebar navigation for roles: ADMIN, ATM-USER, ATM-SPV, BRANCH-ATM-USER, BRANCH-ATM-SPV
11. IF the forecast data API call fails due to a network or server error, THEN THE Forecast_Browser SHALL display an error state with an error message indicating the fetch failed and a retry button to re-attempt the request
12. WHEN the user selects a different Forecast_Date, THE Forecast_Browser SHALL clear all existing row selections and fetch fresh data for the new date

### Requirement 12: Frontend Vendor Request Creation Page

**User Story:** As a Maker, I want a form page to review selected items and finalize a vendor request, so that I can confirm the order details before saving.

#### Acceptance Criteria

1. THE creation page SHALL display the Forecast_Date (read-only), a notes textarea (optional, max 500 characters), and a table of selected items showing: ATM ID, Denomination, Amount Replenish (editable, right-aligned, tabular-nums), and a remove button per row
2. THE creation page SHALL display a summary section showing: total items count and total amount (sum of all amount_replenish values, formatted as IDR currency with no decimal places and dot thousands separator)
3. WHEN the user modifies an amount_replenish value, THE creation page SHALL validate that the value is a positive integer between 1 and 999,999,999 and update the summary on each field change (blur or input event)
4. THE creation page SHALL provide a "Save as Draft" secondary button and a "Submit for Approval" primary button (--red-500)
5. WHEN "Save as Draft" is clicked, THE creation page SHALL call POST /api/v1/vendor-requests to create the request in draft state and navigate to the request detail page on success
6. WHEN "Submit for Approval" is clicked, THE creation page SHALL call POST /api/v1/vendor-requests followed by POST /api/v1/vendor-requests/{id}/submit and navigate to the request detail page on success
7. IF the creation or submission API call fails, THE creation page SHALL display an error toast notification for 5 seconds with the error message and preserve all user input including edited amounts and notes
8. IF the first API call (create) succeeds but the second API call (submit) fails during "Submit for Approval", THEN THE creation page SHALL navigate to the request detail page showing the request in draft state and display an error toast indicating submission failed
9. THE creation page SHALL validate using React Hook Form + Zod that at least one item exists and all amount_replenish values are positive integers between 1 and 999,999,999, and SHALL keep both action buttons disabled while validation errors exist, displaying inline error messages on invalid fields
10. IF a user without one of the roles ADMIN, ATM-USER, or BRANCH-ATM-USER attempts to access the creation page, THEN THE creation page SHALL redirect the user to the dashboard

**User Story:** As a Cash Management staff member, I want a detail page for a vendor request showing full information and available actions, so that I can review, approve, reject, or manage the request.

THE detail page SHALL display: request_number, forecast_date, status badge (using design system badge mapping: draft=neutral, pending_approval=warning, approved=success, rejected=danger, processing=info, completed=success, cancelled=neutral), notes, created_by (full name), created_at, submitted_at, approved_by (full name), approved_at, rejected_by (full name), rejected_at, and rejection_reason, omitting fields that are null (e.g., approved_by, approved_at are not rendered when the request has not been approved)

### Requirement 15: Vendor Request Number Generation

**User Story:** As an operations staff member, I want each vendor request to have a unique human-readable number, so that requests can be referenced in communication with CIT vendors.

#### Acceptance Criteria

1. THE Vendor_Request_Service SHALL generate request numbers following the pattern: VR-YYYYMMDD-NNNN where YYYYMMDD is the forecast_date and NNNN is a zero-padded sequential counter starting from 0001 per forecast_date, with a maximum value of 9999 per date
2. THE Vendor_Request_Service SHALL determine the next sequential number by querying the maximum existing NNNN for the given forecast_date within a database transaction to prevent race conditions
3. IF two concurrent requests target the same forecast_date and a unique constraint violation occurs, THEN THE Vendor_Request_Service SHALL retry number generation with the next available number, up to a maximum of 3 retry attempts
4. IF number generation fails after exhausting all 3 retry attempts, THEN THE Vendor_Request_Service SHALL return an error indicating that the request number could not be generated and SHALL NOT create the Vendor_Request
5. IF the sequential counter for a given forecast_date has reached 9999, THEN THE Vendor_Request_Service SHALL return an error indicating that the maximum number of requests for that date has been exceeded and SHALL NOT create the Vendor_Request
6. THE request_number SHALL be immutable once assigned and remain unchanged through all state transitions

### Requirement 16: Audit Trail for Vendor Requests

**User Story:** As a compliance officer, I want all vendor request actions recorded in an audit log, so that every state change is traceable for regulatory compliance.

#### Acceptance Criteria

1. THE Vendor_Request_Service SHALL write an audit log entry for every state transition containing: entity_type ('vendor_request'), entity_id (vendor_request_id), action (create, submit, approve, reject, revise, cancel, update_items), performed_by (user id), performed_at (ISO 8601 UTC timestamp), previous_state (NULL for 'create' action), new_state, and metadata (JSON object, empty object {} when no extra context applies)
2. WHEN a reject action is performed, THE Vendor_Request_Service SHALL include the rejection_reason in the audit log metadata
3. WHEN items are updated, THE Vendor_Request_Service SHALL include a summary of changes (items_added, items_removed, items_modified counts) in the audit log metadata
4. THE Vendor_Request_Handler SHALL expose GET /api/v1/vendor-requests/{id}/audit-log endpoint returning the list of audit entries for the specified request, ordered by performed_at ascending, with each entry containing: id, entity_type, entity_id, action, performed_by, performed_at, previous_state, new_state, and metadata
5. IF the audit log endpoint is called by an unauthenticated user or a user whose role is not one of ADMIN, ATM-SPV, or BRANCH-ATM-SPV, THEN THE Vendor_Request_Handler SHALL return HTTP 401 for unauthenticated requests or HTTP 403 for unauthorized roles with an error indicating insufficient permissions
6. THE Vendor_Request_Service SHALL treat audit log entries as append-only; no endpoint or service operation SHALL update or delete existing audit log records
7. IF the vendor_request_id referenced in GET /api/v1/vendor-requests/{id}/audit-log does not exist, THEN THE Vendor_Request_Handler SHALL return HTTP 404 with an error indicating the vendor request was not found
