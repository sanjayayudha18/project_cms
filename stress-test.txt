## Ringkasan: apa yang sebenarnya perlu di-stress test

Sebelum ke angka target, ada temuan arsitektur yang mengubah cara kita harus stress test aplikasi ini. Ini penting karena beberapa asumsi umum tidak berlaku di sini:

**Temuan kunci dari kode (bukan asumsi):**

1. **Upload DSR bukan proses in-process Go.** Handler Go memanggil **service Python eksternal** (`service_dsr_etl` di `http://localhost:8090`) secara **sinkron/blocking** lewat HTTP, sampai **25 detik** per fase. Ada dua fase: `POST /uploads` (dry-run) lalu `POST /uploads/confirm` (commit). Parsing Excel + tulis ke DB dilakukan Python, bukan Go. → **Bottleneck 100 upload bersamaan ada di service Python, bukan di Go.** Ini yang paling rapuh.

2. **`WriteTimeout` server = 30 detik**, tapi handler DSR bisa blocking ~25 detik nunggu Python. Di bawah beban, upload DSR duduk sangat dekat dengan plafon timeout. Satu goroutine per upload tertahan selama itu.

3. **DB pool tidak di-tune sama sekali.** `pgxpool.New(cfg.DatabaseURL)` pakai default pgx (max = `max(4, NumCPU)`). Tidak ada `pool_max_conns`. → dengan 500 user, pool default kemungkinan jadi pembatas keras. Ini harus diukur.

4. **Rate limit DSR = 10 upload/jam/vendor.** Jadi "100 upload bersamaan" hanya realistis jika datang dari **≥10 vendor berbeda** (100 upload / 10 per vendor). Kalau dari 1 vendor, 90 akan kena HTTP 429 — itu perilaku benar, bukan bug. Skenario test harus pakai banyak vendor.

5. **Path authenticated murah.** Validasi access token = JWT murni, tanpa Redis/DB. Jadi 500 user yang browsing/list/dashboard akan dibatasi oleh **DB pool tunggal**, bukan auth.

6. **Replica pool belum disambung** — semua read+write ke primary yang sama. `DATABASE_REPLICA_URL` dibaca tapi tidak dipakai. Dashboard "berat" yang harusnya ke replica sekarang menekan primary.

7. **backend-cit hanya health check** — belum ada endpoint nyata, tidak perlu load test berat sekarang.

## Rekomendasi target stress test

**1. 500 concurrent users** — realistis, ini memang NFR (300 concurrent di URS, jadi 500 memberi headroom). Tapi definisikan "user" sebagai *sesi aktif dengan pola campuran*, bukan 500 request identik. Pakai distribusi: ~70% read (list/dashboard/detail), ~20% aksi ringan (approval submit, login), ~10% upload.

**2. 100 upload DSR bersamaan** — bisa, dengan syarat:
- Sebar ke ≥10 vendor (karena rate limit 10/jam/vendor), idealnya 20-50 vendor.
- Yang di-test bukan cuma Go — **service Python ETL adalah subjek utama**. Ukur berapa upload paralel yang bisa ditangani Python sebelum antre/timeout.
- Uji dua fase (dry-run + confirm) karena keduanya blocking.

## Stress test lain yang saya rekomendasikan

| # | Skenario | Kenapa penting | Target awal |
|---|----------|----------------|-------------|
| 1 | **DB pool exhaustion** | Pool default pgx sangat kecil, single primary. Cari titik di mana request antre menunggu koneksi. | Naikkan concurrent read sampai p95 latency meledak; catat angka pool yang benar |
| 2 | **Login/auth burst** | Rate limiter fail-**closed**: kalau Redis lambat/down, semua login ditolak. Uji Redis di bawah beban. | 500 login dalam <1 menit + simulasi Redis latency |
| 3 | **ETL service saturation** | Python ETL adalah dependensi blocking eksternal. Titik jenuhnya menentukan kapasitas upload nyata. | Ramp upload paralel: 10 → 50 → 100, ukur antrean & timeout |
| 4 | **Timeout boundary** | Upload dekat plafon `WriteTimeout` 30s. Uji apa yang terjadi saat ETL sengaja lambat (>25s). | Inject delay di ETL, verifikasi error bersih bukan koneksi menggantung |
| 5 | **Soak test** | Cari memory leak (`io.ReadAll` baca seluruh file ke memori) & kebocoran koneksi. | Beban sedang selama 2-4 jam |
| 6 | **Spike test** | Simulasi deadline DSR jam 09:00 — semua vendor upload berbarengan. | Lonjakan mendadak 0 → 100 upload |
| 7 | **Redis dependency failure** | Redis mati → login & rate limit gagal-tertutup. Uji perilaku degradasi. | Matikan Redis saat beban jalan |
| 8 | **EOD batch vs transactional** | Steering bilang batch & transaksional tak boleh tumpang tindih. Verifikasi resource saat keduanya jalan. | Jalankan `cmd/batch` saat beban transaksional aktif |
